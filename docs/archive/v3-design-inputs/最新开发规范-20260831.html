人类阅读版 · 来源：docs/archive/v3-design-inputs/最新开发规范-20260831.md · 内容哈希：613e1c38e696

从现在开始，对 gpt-market 后续开发采用“最小必要上下文 + 分层架构约束 + Phase/Task 隔离 + 仓库级持久化”的开发模式。

目标：

  1. 显著降低无效 Token / Context 消耗；
  2. 避免 Codex 每次重复扫描整个仓库和全部设计文档；
  3. 让 Codex 专注于当前模块和当前 Task；
  4. 同时防止局部开发逐渐偏离 V3 原始总体设计；
  5. 让开发规范、项目状态和架构约束存在于 Git 仓库中，而不是依赖某一次 Codex 会话或某一台电脑；
  6. 换电脑、重新 clone 仓库、重新开启 Codex 会话后，仍然能够恢复相同开发规则和项目状态；
  7. 尽量让未来 Claude Code、Cursor 或其他 Agent 也能够根据仓库自身信息继续开发。

当前不要重构业务逻辑，不要改变现有已经验收的功能。

本次先完成一次“开发上下文治理”。

一、最高原则：V3 Baseline 仍然是最终 Source of Truth¶

现有 V3 Architecture Baseline 及其正式配套设计仍然是项目最高级设计依据。

本次治理不是重新设计项目。

不得因为减少上下文而：

  • 改变产品目标；
  • 改变 Phase 原始职责；
  • 改变核心业务语义；
  • 绕开已有架构约束；
  • 自行简化重要设计；
  • 为当前实现方便而修改未来架构。

以后普通 Task 不再默认全文读取所有大型文档，但这些文档仍然是最终设计依据。

推荐关系：

V3 Architecture Baseline
        ↓
Architecture Guardrails
        ↓
Phase Capsule
        ↓
当前 Task
        ↓
代码实现

如果下层文档与 V3 Baseline 冲突：

V3 Baseline 优先。

不得静默选择其中一个。

必须报告：

DESIGN_CONFLICT

或：

DESIGN_CHANGE_REQUIRED

二、所有项目级规则必须“仓库化”，不能只存在当前 Codex 会话¶

本次建立的开发上下文治理规则，不得只存在：

  • 当前聊天上下文；
  • 当前电脑 Codex 配置；
  • Codex 临时记忆；
  • 本机未提交文件。

凡属于：

  • 项目级；
  • 跨机器；
  • 跨开发者；
  • 跨 Codex Session；
  • 跨 Agent；

都应该持续有效的规则，必须写入项目 Git 仓库中的版本化文件。

目标：

在一台全新的电脑上：

git clone

项目后，新 Codex 即使没有任何历史对话，也应该能够通过仓库本身知道：

  • 项目总体目标；
  • 当前架构原则；
  • 当前开发到哪个 Phase；
  • 当前 Phase 做到哪里；
  • 下一步做什么；
  • 哪些文件可以改；
  • 哪些东西不能改；
  • 当前模块依赖什么；
  • 如何验收；
  • 如何避免架构漂移。

也就是说：

项目知识属于 Repository
而不是某一次 AI Conversation

三、禁止提交机器特定敏感信息¶

仓库化不意味着把所有东西都提交 Git。

以下内容不得因为本次治理进入 Git：

  • API Key；
  • Secret；
  • Token；
  • 数据库密码；
  • 用户账号；
  • Codex 登录状态；
  • 私钥；
  • 真实交易敏感截图；
  • .env 中真实敏感配置；
  • 当前机器特定 Credential。

必要时只提交：

.env.example

或配置模板。

四、建立 ARCHITECTURE_GUARDRAILS.md¶

创建：

docs/ARCHITECTURE_GUARDRAILS.md

从现有：

  • V3 Architecture Baseline；
  • 需求规格说明；
  • 系统功能架构；
  • 技术架构；
  • 数据库设计；
  • 详细设计；

中提炼真正跨 Phase、长期有效、每个开发任务都必须遵守的核心规则。

要求：

  1. 不复制完整设计文档；
  2. 保持较短；
  3. 建议约 30～50 条核心规则；
  4. 每条使用稳定编号：
G-001
G-002
G-003
...
  1. 只记录真正长期稳定的架构原则；
  2. 后续 Task 可以引用 Guardrail ID。

必须至少覆盖：

基础边界¶

  • V1/V2 必须保持兼容；
  • V3 新功能使用明确独立边界；
  • 不允许为了 V3 随意侵入 Legacy；
  • 业务核心不能强绑定具体模型 SDK。

数据事实¶

  • 系统负责可验证事实；
  • AI 负责综合分析和判断；
  • 用户确认真实资金行为；
  • UNKNOWN 不允许推测填充；
  • stale / conflict / coverage / confidence 必须显式；
  • known_at / as_of 必须防止前视。

Discovery¶

  • Recall 是发现加速器，不是全市场访问权限墙；
  • 未命中 Recall 的股票仍可以完整查询；
  • 不允许使用固定 final_total_score 或等价总分替代 AI 综合判断；
  • Raw Opportunity ≠ Action Candidate；
  • Recall Result 必须可解释；
  • Recall Miss 只能在对应 Horizon 成熟以后生成。

Decision¶

  • Immutable Decision；
  • Review Append-only；
  • Correction 只能追加，不能覆写历史。

Trade / Portfolio¶

  • AI/OCR 不能直接生成真实交易；
  • Screenshot/OCR 只能先生成 Draft；
  • 用户确认后才能成为真实 Trade；
  • Trade Ledger immutable；
  • Opening Position 不允许伪造成历史 BUY；
  • Position 应可以由 Ledger 重建；
  • Portfolio 信息是事实和软偏好，不能成为全市场硬删除机会的规则。

Evidence¶

  • 外部文本属于 Untrusted Data；
  • 外部文本不能控制 Agent Prompt；
  • Opinion 不得自动提升为 Fact；
  • 冲突事实不能偷偷删除。

Strategy¶

  • AI 不得自动激活正式 Strategy；
  • Strategy 变化必须经过 Replay / Shadow / A-B / Guardrail / 用户审批等既定流程。

工程治理¶

  • Schema 版本化；
  • Migration 版本化；
  • Feature 版本化；
  • Prompt / Strategy / Guardrail 等按设计版本化；
  • 不允许因为当前 Task 方便而修改跨模块 Contract。

如果现有正式文档本身存在冲突：

不要自行解决。

记录并汇报。

五、建立开发上下文规范 CONTEXT_POLICY.md¶

创建：

docs/development/CONTEXT_POLICY.md

这份文档专门规定 Codex 后续如何读取上下文。

核心原则：

最小必要上下文
Minimal Necessary Context

不是：

看得越少越好

而是：

只读取完成当前任务真正需要的信息。

六、以后禁止默认扫描整个仓库¶

普通 Task 启动时不得默认：

  • 全仓库搜索；
  • 全文读取所有 Markdown；
  • 全文读取需求规格；
  • 全文读取架构设计；
  • 全文读取数据库设计；
  • 全文读取详细设计；
  • 全文读取所有历史 STATUS；
  • 为了“充分理解整个系统”递归探索所有模块。

只有真正需要的信息才读取。

七、上下文分层读取¶

以后普通 Task 使用以下读取层级。

Level 0：默认上下文¶

必须优先读取：

  1. 根目录 AGENTS.md
  2. 当前目录路径生效的 AGENTS.md
  3. docs/ARCHITECTURE_GUARDRAILS.md
  4. 当前 Phase：
SCOPE.md
CONTRACTS.md
ACCEPTANCE.md
STATUS.md
  1. 当前 Task 描述
  2. 当前 Task 直接相关的源代码
  3. 当前 Task 直接相关测试

绝大部分普通任务应该尽量在 Level 0 完成。

Level 1：直接接口依赖¶

如果 Level 0 不足：

允许读取当前模块直接使用的：

  • DTO；
  • Domain Object；
  • Protocol；
  • Interface；
  • Repository Interface；
  • Service Contract；
  • API Schema；
  • Migration 定义；
  • 配置 Schema。

原则：

优先理解 Contract，
而不是重新理解整个依赖模块。

Level 2：直接依赖实现¶

只有当：

  • Contract 不足以解释行为；
  • 测试失败原因无法从接口判断；
  • 存在兼容性问题；
  • 实际行为和 Contract 不一致；

时，才允许精确读取直接依赖的具体实现。

不要继续递归探索不相关模块。

Level 3：总体设计¶

只有出现：

  • 架构冲突；
  • 跨 Phase 语义不清；
  • Contract 需要改变；
  • 当前文档无法决定；
  • Baseline 一致性需要确认；

时，才读取大型设计文档中的对应章节。

优先精确读取相关章节。

不要默认重新全文阅读所有设计文档。

八、禁止为了节省 Token 猜测接口¶

最小上下文不意味着允许猜。

如果缺少关键事实：

必须精确扩大读取范围。

禁止：

  • 猜字段；
  • 猜接口；
  • 猜数据库结构；
  • 猜其他模块行为；
  • 猜历史设计；
  • 用“应该是”代替事实。

正确方式：

Level 0
↓
不足
↓
Level 1
↓
不足
↓
Level 2
↓
仍存在架构问题
↓
Level 3

而不是：

不知道
↓
自己假设

九、建立 Phase Capsule¶

后续每个 Phase 建立独立目录。

例如：

docs/phases/phase6/

至少包含：

SCOPE.md
CONTRACTS.md
ACCEPTANCE.md
STATUS.md

必要时可以增加：

TASKS.md
DECISIONS.md

但不要无控制增加大量重复文档。

十、SCOPE.md¶

描述当前 Phase：

  • 为什么存在；
  • 负责什么；
  • 不负责什么；
  • 输入；
  • 输出；
  • 前置依赖；
  • 后续消费者；
  • 当前 Phase 边界。

顶部必须明确：

This document is derived from V3 Architecture Baseline.

This document MUST NOT override the V3 Architecture Baseline.

If conflict exists, V3 Architecture Baseline wins and the conflict must be reported.

十一、CONTRACTS.md¶

用于替代普通 Task 每次阅读其他模块大量源码。

只记录当前 Phase 真正需要的跨模块契约，例如：

  • Domain Object；
  • DTO；
  • Repository Protocol；
  • Service Interface；
  • API Contract；
  • 输入字段；
  • 输出字段；
  • Invariant；
  • Error Semantic；
  • Version Requirement。

例如：

FeatureRun
↓
RecallService
↓
RecallRun / RecallResult

只要 Contract 足够完成当前 Task：

不要继续阅读 Feature 内部几十个实现文件。

十二、ACCEPTANCE.md¶

从正式 V3 设计和验收标准中提炼当前 Phase 的验收门槛。

每项必须：

  • 可验证；
  • 可测试；
  • 可以给出 PASS / FAIL；
  • 尽量绑定测试或实际证据。

不能写成：

代码质量不错
功能基本正常

应该类似：

AC-P5-001：
Recall Result 必须返回 channel、reason、rank、version、coverage。

Verification：
自动化测试 + API 示例。

十三、STATUS.md¶

STATUS 是当前 Phase 普通开发过程中的主要进度文档。

建议记录：

Task ID
Task Name
Status
Commit
Tests
Modified Files
Interface Change
Migration Change
Known Issues
Follow-up

状态统一：

TODO
IN_PROGRESS
DONE
PARTIAL
BLOCKED

STATUS 必须简洁。

不要不断复制完整设计内容进去。

十四、建立 Task 模板¶

创建：

docs/development/TASK_TEMPLATE.md

以后禁止使用：

继续 Phase 6
把 Phase 6 做完
继续项目开发
把剩下的全部开发完

这类无限范围任务。

必须拆成明确 Task：

P6-01
P6-02
P6-03
...

一个 Task 尽量只负责一个清晰的软件工程目标。

Task 必须包含：

Task ID
Task Name
Goal
Implements
READ SCOPE
WRITE SCOPE
Dependencies
Acceptance
Tests
Forbidden Changes

十五、每个 Task 建立 Requirement Traceability¶

尽量让 Task 能追溯到正式设计。

例如：

Task:
P6-04 CandidateComparisonPack

Implements:
FR-DI-006

Architecture:
ARCH-x.x

Detailed Design:
DD-x.x

Acceptance:
AC-P6-04-001
AC-P6-04-002

目的：

任何实现都能回答：

为什么写这个？

答案应该是：

为了实现正式需求/架构/验收项。

而不是：

因为 Codex 觉得这样比较好。

十六、READ SCOPE / WRITE SCOPE 必须明确¶

每个 Task 开发前必须明确：

READ SCOPE
WRITE SCOPE

例如：

WRITE SCOPE

app/v3/discovery/**
tests/v3/discovery/**
docs/phases/phase5/STATUS.md

必要时允许读取：

Feature DTO
Feature Repository Protocol
Universe Domain Model

但禁止修改：

V1/V2
Evidence
Context
Trade
Portfolio
Performance
其他无关 Migration
总体架构设计

十七、不要顺手修改其他模块¶

如果发现其他模块存在问题，但：

不阻塞当前 Task

则：

不要修改。

记录：

FOLLOW_UP

到 STATUS。

以后单独建立 Task。

避免：

做 Recall
↓
顺手重构 Feature
↓
顺手改 Repository
↓
顺手改 Context
↓
最终一个 Task 改几十个文件

十八、跨模块 Contract 默认冻结¶

当前 Phase CONTRACTS.md 中已经确认的跨模块接口：

默认视为冻结 Contract。

当前 Task 应：

优先适配 Contract

而不是：

优先修改其他模块。

如果当前 Contract 确实无法满足正式需求：

不得偷偷修改。

必须先输出：

DESIGN_CHANGE_REQUIRED

包括：

当前设计：
...

问题：
...

为什么无法实现：
...

建议修改：
...

影响模块：
...

影响 Phase：
...

API 影响：
...

Database 影响：
...

Migration 影响：
...

V1/V2 Compatibility：
...

是否需要修改 V3 Baseline：
YES / NO

在设计变更正式确认以前：

不要自行扩大修改范围。

十九、AGENTS.md 采用分层结构¶

检查当前仓库 AGENTS 结构。

根：

AGENTS.md

只保留真正全局的项目规则。

不要把完整架构文档复制进去。

根 AGENTS.md 应该非常聚焦，例如：

本项目开发必须遵守：

docs/ARCHITECTURE_GUARDRAILS.md
docs/development/CONTEXT_POLICY.md

普通任务采用最小必要上下文。

不得无目的全仓库扫描。

V3 Baseline 为最终设计 Source of Truth。

任何跨模块 Contract 修改必须显式报告。

每个 Task 必须运行对应测试并更新 Phase STATUS。

然后根据目录建立局部 AGENTS，例如：

app/v3/AGENTS.md
app/v3/discovery/AGENTS.md
app/v3/context/AGENTS.md
app/v3/portfolio/AGENTS.md

具体按项目现状决定，不要为了形式机械创建大量 AGENTS。

原则：

越靠近具体模块，
规则越聚焦。

不要在每层重复相同的大段文本。

二十、普通开发 Task 的标准执行流程¶

以后每个 Task：

1. 读取最小上下文
2. 确认 READ / WRITE Scope
3. 查看当前 Task 相关代码
4. 给出简短实现计划
5. 只完成当前 Task
6. 写/修改对应测试
7. 运行当前模块测试
8. 必要时运行最小回归测试
9. 修复失败
10. 更新 STATUS
11. Git commit
12. 停止

不要自动进入下一 Task。

二十一、一个 Task 完成以后不要长期背着旧上下文¶

Task 完成以后：

把真正需要保留的信息写进仓库：

代码
测试
STATUS
Contract
必要文档
Commit

后续新 Task 应重新从仓库恢复状态。

不要依赖：

上一次 Codex 对话还记得。

二十二、建立轻量 Contract Check¶

每完成若干互相关联的 Task，例如 3～5 个关键 Task：

执行一次：

Contract Check

只检查：

  • 接口是否漂移；
  • Input/Output 是否一致；
  • 是否出现重复模型；
  • 是否修改冻结 Contract；
  • 是否突破 Phase 边界；
  • 当前实现是否仍满足 Guardrails。

Contract Check 不需要每次全文读取整个项目。

二十三、每个 Phase 必须执行 Phase Gate¶

普通 Task 使用局部上下文。

但是当一个 Phase 宣称完成时：

必须单独执行：

Phase Architecture Conformance Review

Phase Gate 允许扩大上下文。

至少重新对照：

  • V3 Architecture Baseline；
  • Architecture Guardrails；
  • 当前 Phase SCOPE；
  • CONTRACTS；
  • ACCEPTANCE；
  • STATUS；
  • 当前 Phase 实际代码；
  • Migration；
  • API；
  • Tests；
  • 与前后 Phase 的接口。

必须检查：

  1. 是否漏需求；
  2. 是否偏离原始设计；
  3. 是否改变业务语义；
  4. 是否突破当前 Phase 边界；
  5. 是否提前侵入未来 Phase；
  6. 是否存在重复实现；
  7. 是否产生不必要跨模块耦合；
  8. 是否违反 known_at；
  9. 是否伪造 UNKNOWN；
  10. 是否修改冻结 Contract；
  11. 是否与数据库设计冲突；
  12. 是否破坏 V1/V2；
  13. 是否违反 Architecture Guardrails；
  14. 是否全部满足 ACCEPTANCE；
  15. 是否有真实测试证据；
  16. 是否有遗留 BLOCKER。

只有 Phase Gate 正式通过：

才允许把该 Phase 标记为：

DONE / ACCEPTED

二十四、把重要架构原则逐渐变成自动测试¶

不要完全依赖 Codex 每次记住文档。

适合自动验证的架构规则应该逐渐变成测试。

例如：

known_at <= as_of

UNKNOWN 不得自动补值

Recall 不限制 Full Universe Query

禁止 final_total_score

Raw Opportunity != Action Candidate

Decision immutable

Review append-only

Trade Ledger immutable

Trade 必须用户确认

OCR 只能生成 Draft

二十五、大型文档更新策略¶

普通 Task 不再每次修改所有大型设计文档。

如果 Task 没有产生真实架构或 Contract 变化：

主要更新：

  • 当前代码；
  • 当前测试；
  • STATUS；
  • 必要局部文档。

不要每完成一个小功能就全文修改：

  • Requirements；
  • Architecture；
  • Technical Architecture；
  • Database Design；
  • Detailed Design；
  • 所有状态文档。

否则文档本身会继续成为 Token 黑洞。

二十六、发生正式设计变化时必须同步 Source of Truth¶

减少文档更新不意味着允许文档过期。

如果发生真实：

  • Requirement Change；
  • Architecture Change；
  • Contract Change；
  • Schema Change；
  • Phase Boundary Change；

必须同步正式 Source of Truth。

不能只写：

STATUS.md

然后让总设计永久过期。

  • Technical Architecture；

  • Detailed Design；
  • Feature Status；
  • Work Status；

哪些因为本 Phase 的真实实现需要同步。

这样把“大文档全局同步”从：

每一个 Task

降低成：

每一个 Phase 少数几次

二十九、换电脑后的恢复标准¶

本次治理完成以后，以以下场景作为验收标准：

假设：

  1. 当前电脑完全不可用；
  2. 新电脑安装 Git 和 Codex；
  3. clone 当前 Repository；
  4. 不提供旧 Codex Conversation；
  5. 不人工重新解释整个项目。

新的 Codex 应该能够：

  1. 读取根 AGENTS；
  2. 找到 Architecture Guardrails；
  3. 找到 Context Policy；
  4. 找到当前 Phase；
  5. 找到 STATUS；
  6. 知道当前完成了什么；
  7. 知道下一 Task 是什么；
  8. 知道哪些接口被冻结；
  9. 知道哪些文件可以修改；
  10. 知道如何验收；
  11. 知道不能违反哪些全局设计原则。

如果做不到：

说明项目仍然过度依赖旧 Session，需要继续治理。
