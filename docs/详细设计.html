gpt-market V3 详细设计¶

基线：V3 Architecture Baseline 1.0 状态：实施前模块与接口设计；当前代码映射来自仓库实审，V3 模块尚未创建。

1. 设计范围¶

本文把架构拆成可实现模块、用例、接口契约、后台任务、错误语义和测试要求。Phase 顺序和总体边界以《架构设计实施稿》为准，数据库字段以《数据库设计》为准。

2. 当前模块映射¶

当前模块 责任 V3 处理方式
app/main.py FastAPI/FastMCP 生命周期、MCP Bearer 保留，挂载独立 V3 Router
app/container.py Service/Provider 单例装配 保留，增加 V3 Container/Repository
app/providers/* Eastmoney/Tencent 解析与标准化 保留，不直接承载 Evidence
app/services/market_data_service.py Provider Fallback、Kline L1/L2 Legacy 继续使用，V3 通过 Adapter 复用
app/services/scanner.py V1/V2 扫描与 Coverage 保留，不改评分；V3 Discovery 独立
app/fundamentals/* Phase2A 基本面主/备源 作为 V3 Fundamental 输入适配
app/api/live.py 后台快照、预序列化 HTML 保留，Handler 只读缓存
app/api/v2_dashboard_cache.py 后台 V2 扫描缓存 保留
app/kline_cache.py SQLite Kline Legacy 保留，迁移副本标记 Approx
app/history.py Scan JSONL Legacy 保留，V3 用正式 Observation

3. V3 核心接口协议¶

所有 Application Service 使用显式输入/输出 DTO；Domain 不返回 FastAPI Response。Repository 和 Provider 使用 Protocol/ABC，测试注入 Fake。

通用事实字段：

source, upstream_source, source_type,
event_time/report_period, publish_time, fetch_time, known_at,
confidence, coverage, stale, error, content_hash, revision_id

未知值使用 null + 状态/错误，不使用 0、空字符串或推测值代替。

4. Universe 模块¶

4.1 接口¶

class UniverseProvider(Protocol):
    async def fetch_snapshot(self, as_of: datetime) -> UniverseFetchResult: ...

class UniverseService:
    async def refresh(self) -> UniverseSnapshot: ...
    async def latest(self, allow_lkg: bool = True) -> UniverseSnapshot: ...

4.2 刷新流程¶

  1. 调用 Primary；
  2. 校验证券数量、代码唯一性、市场分布和字段覆盖；
  3. 失败时调用 Secondary；
  4. 全部失败时读取 LKG；
  5. 计算 Diff；
  6. 在短事务中发布 Snapshot；
  7. LKG 必须标记 stale=true。

异常：覆盖骤降、重复代码、Provider 空数据均视为失败，不发布为最新。

5. Bar 与 Feature 模块¶

5.1 Bar Ingestion¶

按证券批次拉取 raw/unadjusted 日 K 和 Factor。网络 I/O 与标准化在事务外；每批生成 Revision，校验日期递增、OHLC 关系、负数、重复和缺口后发布。

5.2 Derived Series¶

前/后复权序列由 Raw + Factor 派生并绑定 Revision。只能获得前复权时写 LIMITED，不得补造 Raw。

5.3 Feature Run¶

输入：Universe Snapshot、Bar Revision Set、Feature Version、as_of。

输出：每证券轻量 Feature、Coverage、Missing Fields、Run Hash。Run 状态：PENDING/RUNNING/VALIDATING/PUBLISHED/FAILED。只有 Published 可被 Query/Recall 使用。

5.4 Full Universe Query¶

过滤表达式只允许字段和操作符白名单；Cursor 包含 Feature Run ID 和最后排序键。请求下一页时 Run 不变。默认 50、最大 500。

6. Market Regime 模块¶

从 Published Feature、指数和市场宽度生成结构化事实。模块不得返回 allow_buy=false 等固定权限。风险事件仅引用 Evidence IDs。

7. Recall 与 Candidate Comparison¶

7.1 Recall Channel¶

每个 Channel 实现相同协议：

class RecallChannel(Protocol):
    code: str
    version: str
    def evaluate(self, feature_view: FeatureView) -> list[RecallHit]: ...

输出原因、命中特征、strength 和 channel rank。MultiRecallService 合并但不删除未命中证券。

7.2 CandidateComparisonPack¶

输入 Candidate Set（20–100）、字段 Profile、Snapshot IDs；输出统一紧凑表。不得调用单股深度 Evidence 或分钟 K。Pack 完成后由 ChatGPT 输出 CandidateComparisonResult 和 TopK，再为 TopK 构建 NORMAL/DEEP Context。

7.3 Recall Miss¶

Job 只处理已成熟 Horizon。优秀机会阈值绑定版本，结果关联原 Recall Run 和 Feature Run。

8. Evidence 模块¶

8.1 Provider 与 Fetch¶

每种数据类型配置 Provider 优先级、限流、重试和缓存。Fetch 先落 Raw，再触发 Parse。Raw 写入成功前不得只保留解析结果。

8.2 Parse / Dedup / Entity Link¶

  • Parser 按 Source + Version 注册；
  • 精确 Hash 去重后再做近似重复；
  • 更新公告保留独立记录并关联前版本；
  • Entity Link 低置信时只保存候选，不自动关联证券；
  • 时间字段不可证明时保持 UNKNOWN。

8.3 Conflict¶

同一命题多源冲突形成 Conflict Set。系统计算来源优先级和置信度但不删除低优先级事实。Opinion 永不升级为 Fact。

8.4 Untrusted Boundary¶

Raw 文本进入 Context 时使用明确数据标签和长度限制，过滤脚本/HTML，禁止把其中“忽略系统指令”等文本放入 Agent Instruction 区。

9. Context 模块¶

9.1 Builder¶

build_fast(subject, as_of)
build_normal(subject, as_of)
build_deep(subject, as_of)
build_candidate_comparison(candidate_set, as_of)

Builder 按任务 Profile 收集事实，记录所有候选 Evidence 及最终 Selection。真实持仓、交易、Stop/Cancel、反方 Evidence、质量和冲突不可被预算裁掉。

9.2 Hash¶

对规范化 Payload、所有 Revision IDs、Selection 顺序和 Builder Version 计算 Hash。AI 导入必须回传并重新验证。

10. Task 模块¶

Profile 包含 Schedule、Timezone、Trading Calendar、Context Level、Comparison/TopK 和 Schema。Scheduler 根据交易日历产生 Expected Run，不调用 AI。用户或 ChatGPT 完成分析后通过 Import 更新 Task Run。

状态：EXPECTED/PENDING_IMPORT/COMPLETED/MISSED/CANCELLED。失败 Atomic Group 对应 Task Run 保持 Pending/错误状态，成功组完成。

11. AI Result Import¶

11.1 Parse 与 Preview¶

  1. 判断 Single/Bundle；
  2. 校验 Bundle Hash/Agent Identity；
  3. 校验 Atomic Group 边界；
  4. 逐组解析 Result Schema；
  5. 校验 Task、Context Hash、Evidence、known_at 和依赖；
  6. 生成不可变 Preview Revision；
  7. 返回每组将创建对象和错误。

11.2 Confirm¶

Confirm 请求包含 Import ID、Preview Revision、Bundle Hash、Idempotency Key。服务按组开启事务；组内创建对象、依赖、Task 状态和 Audit 全部成功后提交。最终返回 successful_groups 和 failed_groups。

11.3 结果映射¶

Result 允许写入 禁止行为
MarketReview append-only MarketReview 禁止市场买卖硬开关
CandidateComparisonResult TopK/比较结论 禁止写真实交易
DecisionResult Decision、Watchlist、EntryPlan 禁止修改旧 Decision
ReviewResult Review、Watchlist Event 禁止实际 SELL
PositionReviewResult Position Review/建议 禁止改 Ledger

12. Watchlist / Decision / Review¶

Watchlist 当前状态是 Event 投影。Decision 创建后冻结。Review 引用 Previous Review 形成链。Correction 只能追加，并保留原 Hash。

状态变更必须验证：无真实 BUY 不能进入 HOLDING；Target/Stop 信号不能变成 CLOSED；部分 SELL 后仍按 Ledger 数量判断。

13. Trade 与 Portfolio¶

13.1 Manual Trade¶

输入证券、账户、BUY/SELL、价格、数量、时间、费用和可选 Decision/Entry。预览校验超卖、重复、市场代码和计划偏差，用户确认后写 Ledger。

13.2 Image Import¶

保存图片 Hash/Reference，OCR 输出字段级 Confidence 和 Region。系统只创建 Draft。持仓截图生成 Opening/Position Draft，不反推历史 BUY。

13.3 Projection¶

按 Account + Security 重放 Opening、Adjustment、Trade、Correction。Projection 保存最后 Ledger Sequence。校验任务定期从头重建抽样并比较。

13.4 Execution Deviation¶

  • Price：相对计划最近边界；
  • Time：相对 Entry Window；
  • Quantity：相对计划数量/仓位；
  • Trigger：真实成交时触发条件是否成立；
  • Cancel：是否违反取消条件。

14. Performance 与 Replay¶

Observation Job 在 Horizon 成熟后写未来收益、MFE/MAE、Target/Stop。归因分别写 Selection、Entry Plan、User Execution、Add、Reduce、Exit、Risk Control。

Replay Loader 只能读取 known_at <= as_of 的 Revision/Evidence/Context。发现未来泄漏立即 BLOCKED，不能降级为普通 Warning。

15. API 设计约定¶

  • V3 前缀 /api/v3；
  • JSON 字段使用 snake_case；
  • 时间 ISO 8601 含时区；
  • 列表使用 Cursor，不使用不稳定 Offset；
  • 错误结构：code/message/request_id/details/retryable；
  • READ 返回 Snapshot/Run/Revision/Quality；
  • WRITE 支持 Idempotency Key；
  • HTML 与 JSON 分离，HTML 不作为契约。

16. 后台任务¶

Job 触发 失败策略
Universe Refresh 交易日/日终 Provider Fallback + LKG
Daily Bar Increment 收盘后/补数 批次重试、游标续跑
Feature Run Bar Published 后 旧 Published Run 继续可读
Market Regime Feature Published 后 保留上一份并标 stale
Recall Run Feature/Regime 后 单通道失败显式记录
Evidence Core 按源 Schedule Raw 保留、解析可重跑
Expected Run Update Task Profile Schedule 只改 Registry，不执行 AI
Performance Mature 每交易日 仅成熟 Horizon
Projection Verify 定时/交易后 报警，不静默修正 Ledger

17. 配置¶

V3 配置分组：Database、Migration、Worker、Universe、Bar、Feature、Recall、Evidence、Context Budget、Task Schedule、Storage、Security、Feature Flag。Secret 只通过环境/Secret Store，不进入数据库配置 JSON 或 Git。

配置变更保存版本与生效时间；Strategy/Guardrail 不使用普通环境变量静默修改。

18. 测试设计¶

18.1 单元测试¶

Domain 不变量、Hash、时间、Filter Parser、Feature、Recall、Dedup、Conflict、Context Trim、Ledger Projection、Execution Deviation。

18.2 集成测试¶

PostgreSQL Repository、Migration Up/Down/Restore、Atomic Group 部分失败、Idempotency、Provider Fallback、Worker Resume。

18.3 契约测试¶

Agent Envelope/Bundle、READ API、错误结构、MCP/Web parity、V1/V2 兼容。

18.4 Replay 测试¶

冻结 Clock，构造未来 Evidence/Revision，验证读取被拒绝；601233 在缺资料时保持 Blocked。

19. 发布步骤¶

每个 Phase：任务分支 → 状态登记 → 最小实现 → 测试 → 文档/状态 → 中文提交 → 推送 → Review → Feature Flag Shadow → 验收 → 合并/部署。数据库变更先备份与 Migration 验证，任何失败可关闭 V3 而不影响 V2。

20. 未决项¶

PostgreSQL ORM/Driver、Scheduler、Raw Storage、OCR、Secondary Universe、交易日历均为 UNKNOWN，Phase 实施时通过 ADR 决定。本文不为这些项目编造现状。
