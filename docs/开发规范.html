gpt-market 开发工作规范¶

本规范用于防止换电脑、换模型、上下文压缩或 Token 额度中断造成工作丢失。所有参与者（用户、Codex、其他模型和人工开发者）均应遵守。

1. 文档职责¶

  • README.md：项目入口、当前能力和接手阅读顺序；
  • docs/架构设计实施稿.md：V3 唯一架构基线，回答“要建设什么、边界是什么”；
  • docs/开发规范.md：固定协作规则，回答“每一步应该怎样做”；
  • docs/工作状态.md：唯一实时进度入口，回答“已经做了什么、正在做什么、下一步是什么”；
  • 当前代码与测试：功能真实状态的最终依据；
  • docs/archive/：历史设计输入和 V1/V2 过程材料，默认不作为新任务必读内容。

架构基线、工作状态和代码发生冲突时，不允许静默选择。先在工作状态中记录冲突，再由用户确认以代码现状、架构基线或新决策中的哪一个为准。

2. 换电脑或换模型的接手顺序¶

新环境开始工作前必须依次阅读：

  1. 根目录 README.md；
  2. docs/架构设计实施稿.md；
  3. docs/开发规范.md；
  4. docs/工作状态.md；
  5. 与“下一步”直接相关的代码、测试和当前参考文档；
  6. 查看 git status、当前分支、最近提交和远端同步状态。

默认不读取 docs/archive/。只有需要追溯 V1/V2 设计原因、历史验收证据或 V3 Review 原文时，才按 docs/README.md 的索引定向读取。

3. 开始任务前¶

每个任务开始前执行并记录：

git status --short --branch
git log -5 --oneline
git remote -v

然后：

  1. 核对 docs/工作状态.md 中的当前阶段、下一步和阻塞项；
  2. 明确本次允许修改的范围和明确禁止项；
  3. 检查工作区已有改动，禁止覆盖或误提交他人的文件；
  4. 将本次任务写入“进行中”，再开始实现；
  5. 功能开发优先使用 codex/<phase>-<feature> 分支；纯文档和用户明确允许的极小修订可以直接在主分支完成。

4. 小步开发与 Git 检查点¶

“一步”必须是可以说明、验证和独立恢复的最小工作单元，例如：

  • 一个数据模型及其测试；
  • 一个数据库迁移及回滚验证；
  • 一个 Provider 能力及降级测试；
  • 一个 API 契约及契约测试；
  • 一项文档结构整理。

每完成一步，必须按以下顺序操作：

  1. 运行与改动风险相匹配的测试或检查；
  2. 更新 docs/工作状态.md：完成内容、验证结果、剩余事项、已知问题；
  3. 检查 git diff，确认没有 Secret、运行数据或无关改动；
  4. 使用中文提交说明提交；
  5. 立即推送到 GitHub；
  6. 核对本地 HEAD 与远端分支一致；
  7. 再开始下一步。

推荐提交格式：

阶段：动作和结果

示例：
文档：建立开发状态与归档规范
Phase1：新增Evidence基础表与迁移测试
修复：纠正Context Hash校验失败
测试：补充Bundle分组原子性用例

一个提交只承载一个清晰目的。禁止把多个无关功能、格式化和临时调试混在同一提交。

5. Token、时间或外部条件即将中断时¶

不能为了“提交完整功能”而让未记录的工作消失。若功能尚未完成：

  1. 停止扩大改动范围；
  2. 将代码保持在独立任务分支，不把不可用状态合并进 main；
  3. 在 docs/工作状态.md 写清：已完成、未完成、当前失败、关键文件、执行过的命令、下一条可直接执行的动作；
  4. 能通过局部测试时创建中文检查点提交；
  5. 必须保留不完整代码时，使用 WIP：<当前检查点> 提交到任务分支并推送；
  6. 明确标记该分支不可发布、哪些测试未通过；
  7. 新会话从该分支和工作状态继续，不重复猜测上下文。

main 只接收通过当前阶段验收的完整步骤。WIP 提交不得部署，不得作为阶段完成标记。

6. 工作状态记录要求¶

docs/工作状态.md 必须保持短、准、可接手，至少包含：

  • 当前基线、分支、最近稳定提交；
  • 当前 Phase 和授权状态；
  • 已完成；
  • 正在进行；
  • 未开始；
  • 阻塞项与 UNKNOWN；
  • 最近验证命令和结果；
  • 下一步的第一条可执行动作；
  • 关键文件；
  • 部署状态（如本任务涉及部署）。

状态文档不是流水账。详细历史由 Git 提交和归档文档承担；状态文档只保留当前接手所需信息和少量最近里程碑。

7. 测试与完成定义¶

一步只有同时满足以下条件才算完成：

  • 实现范围符合架构和用户授权；
  • 相关自动化测试通过；
  • 必要的真实数据/接口验证已执行，或明确说明为何无法执行；
  • 未破坏 V1/V2、MCP、行情和已有 API 的兼容性要求；
  • 文档和工作状态已更新；
  • 提交说明为中文；
  • 已推送 GitHub，并确认远端提交；
  • 若涉及部署，健康检查、关键端点和回滚路径已验证。

测试失败、Coverage 不足或外部源不可用时，禁止用“应该可用”代替结果；必须在工作状态中记录实际错误与影响。

8. 安全与禁止提交内容¶

禁止提交：

  • .env、Token、密码、服务器私钥和真实鉴权 Secret；
  • 用户账户、真实交易截图和敏感 Portfolio 数据；
  • tmp/、渲染中间文件、无必要的运行缓存；
  • 未确认授权的服务器配置变更；
  • 把 UNKNOWN 猜成确定事实的文档或代码。

提交前至少执行：

git status --short
git diff --check
git diff --cached --check
git diff --cached --name-only

9. 文档分类与生命周期¶

  • Baseline：当前唯一实施依据，只保留一份有效基线；
  • Working State：持续覆盖更新，不按日期复制多份；
  • Reference：当前 API、部署、测试和字段说明，按需阅读；
  • Archive：历史版本、验收报告和设计输入，只读保存；
  • Generated Evidence：探针和验收脚本产生的样例，必须标明时间，不能当作当前行情。

新架构基线正式通过后，旧基线移入对应 Archive；不得让两份文档同时声称自己是当前基线。

10. 回滚与交接¶

每项功能在开始前明确回滚点，优先通过独立分支、Feature Flag、可逆 Migration 和追加式数据变更降低风险。交接时只需提供：

  1. Git 分支和远端提交；
  2. docs/工作状态.md；
  3. 未通过的测试或阻塞证据；
  4. 下一条可执行动作。

任何新模型或新电脑不得仅依靠聊天记录继续开发；GitHub、架构基线、工作状态、测试和代码才是可恢复的共同记忆。
