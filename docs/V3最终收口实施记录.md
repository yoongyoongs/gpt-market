## 1. 状态定义

- `DESIGN_ONLY`：仅有设计，没有可验证实现；
- `CODE_COMPLETE`：代码已完成，尚未完成要求的技术验收；
- `TECH_ACCEPTED`：模块级 Domain/Repository/API/专项测试已通过；
- `PRODUCTION_DATA_READY`：生产数据已生成并完成覆盖、质量和运行证据验收；
- `PRODUCT_CLOSED`：横向日常使用闭环及 Product Closure Gate 已通过；
- `BLOCKED`：存在明确外部依赖或设计冲突，当前无法继续。

`TECH_ACCEPTED` 不等于 `PRODUCT_CLOSED`。Phase 1–11 的历史验收记录不回写成“当时未完成”，收口工作只补齐真实横向链路。

### 2026-09-02：RC-08D 幂等矩阵（§11.5）

- 问题（整改方案 §11.5）：每个 WRITE 必须有稳定幂等策略、对外契约可重复请求；逐项核对发现多个写路径的"content_hash 去重"失效——因为 content 包含服务端 `default_factory=uuid4` 的主键，同一业务请求重复提交会生成不同 hash：要么静默双写（adjustment/reconciliation/correction/health event），要么撞业务唯一约束抛裸 `UniqueViolationError`（→500，opening/strategy version），或重复消费序列（experiment event）；
- 幂等矩阵（核对结果 + 修复后契约）：

| 操作 | 幂等策略（实现） | 修复 |
|---|---|---|
| AI Confirm | `idempotency_key` 唯一（uq_ai_import_idempotency）；重复同 key 返回当前状态，不同 key → 409；atomic group commit 返回已有 result_id | 无需修复（已幂等） |
| Trade Confirm | ledger `idempotency_key` 预查 → 返回原 trade_id | 无需修复（已幂等，新增回归测试固化） |
| Opening | 业务身份 (account, security, baseline_time) 预查：内容一致 → 返回原 id；内容不同 → `RepositoryConflictError`（409） | ✅ 修复 |
| Adjustment | content hash（剔除自增 PK）预查 → 返回原 id | ✅ 修复 |
| Correction | content hash（剔除自增 PK）预查 → 返回原 correction_id，不消费新序列、不触达状态机 | ✅ 修复 |
| Reconciliation | content hash（剔除自增 PK）预查 → 返回原 id | ✅ 修复 |
| Strategy version | (strategy_code, version) 身份预查：内容（configuration/rationale/created_by/supersedes）一致 → 返回原 id；不同 → 409 | ✅ 修复 |
| Experiment event | 与最新事件 (event_type, actor_id, reason) 完全一致的重复请求 → 返回原事件 id（重放无副作用）；否则仍走状态机校验 | ✅ 修复 |
| Health event | content hash（剔除自增 PK）预查 → 返回原 id，不重复触发 rollback 判定 | ✅ 修复 |

- 实现要点：所有修复都在仓储层预查去重（add_if_absent 语义），无 schema 变更；content_hash 组成对上述表剔除服务端自赋主键（老数据存量 hash 不受影响——全库无任何按重算 hash 校验旧行的逻辑，已核实）；重复请求统一返回原实体 id（200），同身份不同内容统一 409（V3_CONFLICT envelope），对外契约稳定可重复；
