## 1. NEW-SEC-001：Public READ 收紧为 Market READ Allowlist ✅

### 问题（复验报告 §3.1 / §4）

`V3AuthPolicy.required_scope()` 旧逻辑：GET 仅 `/portfolio` 前缀要 `PORTFOLIO_READ`，
其余全部 GET 匿名公开——`/watchlist`、`/decisions`、`/reviews`、`/performance`、
`/task-runs`、`/task-context/{profile}`、`/strategies*`、`/strategies/releases/{env}`、
`/release/resolution`、`/entry-plans/{id}/versions`、`/watchlist/changes`、
`/stocks/{id}/decision-pipeline`、`/portfolio-preferences`（别名绕开）等私有/控制面
数据全部可匿名读取。

### 方案

黑名单不可持续（新路由默认公开）。改为**默认拒绝 + 显式 Allowlist**：

- `app/v3/security.py` 新增模块级常量与函数：
  - `PUBLIC_MARKET_READ_EXACT`：纯市场事实精确路径
    （`/universe/features`、`/universe/query`、`/market-regime`、`/market-overview`、
    `/candidates/comparison-pack`、`/recalls`、`/recalls/misses`、`/raw-opportunities`、
    `/market-reviews`、`/market/intraday-status`、`/health/data-quality`）；
  - `PUBLIC_MARKET_READ_PREFIXES`：`/evidence/`、`/context-packs/`；
  - `PUBLIC_MARKET_READ_TEMPLATES`：通配段模板 `("stocks","*","evidence")`、
    `("stocks","*","context-pack")`（按 `/` 分段匹配，`*` 匹配单段）；
  - `is_public_market_read(path)`：接收去掉 `/api/v3` 前缀的相对路径。
- `required_scope()` 新逻辑：
  - 非 `/api/v3` → None（不变）；OPTIONS → None（不变）；
  - 非 GET/HEAD → `V3_WRITE` / `STRATEGY_ADMIN`（不变）；
  - `/portfolio` 前缀 → `PORTFOLIO_READ`（不变）；
  - **`/portfolio-preferences` 别名 → `PORTFOLIO_READ`**（封住别名绕开）；
  - `public_market_read=True` 且命中 allowlist → None（匿名）；
  - **其余 GET/HEAD → `MARKET_READ`**（任何有效 token 均持有该 scope，
    匿名一律 401；`public_market_read=False` 时全量 GET 仍 `MARKET_READ`，语义不变）。

### 测试（tests/v3/test_v3_auth.py）

- 新增 `PUBLIC_MARKET_PATHS`（11 条 allowlist 路径）匿名 200 矩阵；
- 新增 `PRIVATE_READ_PATHS`（10 条私有/控制面路径）匿名 401 且
  `required_scope == MARKET_READ`；同路径带 token 200 矩阵；
- `/portfolio-preferences` 别名：匿名 401、token 200 且 principal 注入；
- 原 `test_market_read_can_be_protected_by_configuration`（全量保护开关）保留通过。

### 连带修复

- 新增 `tests/conftest.py`：测试进程固定 `V3_API_TOKEN`（os.environ 优先级高于
  `.env`，且先于 `app.main` 导入生效），避免收紧后依赖开发者本地 .env 差异；
- `tests/v3/test_error_envelope.py`：走真实 `app.main` middleware 的
  `_test/*` 错误矩阵、watchlist 校验错误、未知路由 404 改为带 token 请求
  （错误断言本身不变）。

### 结果

`tests/v3` 全量：**329 passed, 89 skipped**（原 325 passed，+4 为新增矩阵测试）。

## 4. NEW-OPS-002 + NEW-OPS-003：Catch-up 终端标记 + as_of 语义 ✅

### 问题（复验报告 §3.2 / §4）

- `_latest_main_success_key()` 取 `features` 的最近成功幂等键作为追平标记；
  主链已扩为 5 Job，features 成功而 evidence-increment/full-recall 失败时，
  下一轮调度会把该交易日误判为已追平，后半链永远不再补跑（P1）；
- 历史 pending date 共用 `as_of=now`，且 Job 标签是旧日期——补跑事实被误读为
  历史时点快照，破坏 Point-in-Time 语义（P1）。

### 修复（scripts/v3_scheduler.py）

- 新增常量 `TERMINAL_MAIN_JOB = "full-recall"`；
  `_latest_main_success_key()` 改查终端 Job，docstring 说明 5 Job 主链；
- 新增 `_annotate_catchup_runs(trade_date, pending_dates, runs)`：每个主链运行
  报告标注 `catchup_mode`——历史日期 `operational-catchup`、当日 `same-day`；
  不改动 orchestrator 原始键（浅拷贝后附加）；
- `run_once` 报表新增顶层 `catchup_mode`：
  `operational`（存在历史补跑日）/ `same-day`；
- 语义裁决（对齐报告"两种模式必须分开"）：
  **scheduler catch-up = operational 补数**（按当前可见数据补齐缺失事实、
  按 trade_date 幂等防重，as_of 统一为本次运行时刻）；
  **historical point-in-time 重建 = Deterministic Replay（PF-02）职责**，
  调度器绝不声称历史时点。

### 部署语义说明

切换终端标记后，若生产存在"features 成功、full-recall 未成功"的历史日，
首次运行会自动把它们列为 pending 重补——已成功 Job 幂等 SKIPPED，
只补 evidence-increment/full-recall，成本可控。

### 测试（tests/v3/test_scheduler.py）

- `test_catchup_terminal_marker_uses_full_recall`：monkeypatch UoW 捕获
  实际查询的 job_id，断言 `full-recall`；
- `test_annotate_catchup_runs_marks_historical_dates`：历史/当日混合标注、
  原始报告不被修改；
- `test_run_once_report_is_json_serializable` 保留通过（报表新增键不破坏序列化）。

### 结果

`tests/v3` 全量：**332 passed, 89 skipped**。

## 6. PF-001 七类归因关键部分 + NEW-PF-001 空集合兜底 ✅
